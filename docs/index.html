The problem

Every contract deployment is a leap of faith.

Nothing on Stellar links the bytecode running on-chain to the source everyone reviewed. Until now.

Trust by README is not security.

When a Soroban contract goes live, the only link between deployed WASM and its source repo is a claim. Worse, Soroban's executable_update flow lets a contract be silently replaced — with no reconstructed history and no proof of what ran.

veriseal makes "this on-chain bytecode came from this commit" machine-verifiable, CI-enforced, and checkable by anyone.

  • Deployed code differs from audited sourcesupply-chain drift, compromised release, wrong artifact
  • Silent upgrades no one can traceexecutable_update history reconstructed nowhere
  • Non-reproducible builds shipunpinned deps, timestamps, host-dependent codegen
  • Bytecode ⟷ source proven & sealedthis is what veriseal does — for every deploy
How it works

One tool across the whole contract lifecycle.

Build, CI, release, deploy, audit — provenance at every step, no other Stellar tooling required.

1

Seal

veriseal record hashes artifact, source, toolchain & commit into veriseal.provenance.json.

2

Verify

veriseal verify rebuilds from a clean tree and fails on any drift. CI gate + SARIF.

3

Sign

Ed25519-signed in-toto attestations (SLSA v1.0, DSSE). Verifiable by public key alone.

4

Deploy

veriseal onchain-verify reads the live WASM hash straight off the ledger via Soroban RPC.

5

Audit

veriseal onchain-audit reconstructs full upgrade lineage and flags unsealed versions.

6

Registry

Paste any contract address → provenance, source hash & history. Public, read-only, free.
